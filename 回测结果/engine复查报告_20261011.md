## 二、记账与权益口径（#196）

### 2.1 核心判据：不存在自建逐 bar 权益累加

```
grep -c 'equity\s*[+-]=' lib/engine.py  →  0
```

这正是历史「记账 bug 家族」的第一判据（`equity += pos*(X[i]-X[i-1])*MULT` 逐 bar 累加 ⇒ 顺势策略系统性虚高）。
engine 全文命中 0 行 ⇒ **结构性免疫**，不是「写得小心」而是「根本没有这个写法」。

### 2.2 权益的三个来源，各司其职

| 用途 | 取数 | 行号 |
|---|---|---|
| 画图 | `equity_curve.append((bar_dt, float(account.balance)))` | L1007 / L2600 等 |
| 统计 | `stat = sim.tqsdk_stat` | L1367 / L2783 / L3979 / L4849 / L5797 |
| 算手数 | `_risk_equity_base` 用 `account.balance` | L400 附近 |

三者互不干扰：画图序列**不参与**任何统计或手数计算。

### 2.3 已处理 tqsdk 的关键坑

```python
# L1340-1347
# ★ 必须先关掉 api：tqsdk 是**在 close 时**才结算 tqsdk_stat 的。
#   不先关就往下走，stat 读到的全是 0（实测：报告收益率 0.00%、结束资金 0）
try:
    _兜底局部["api"].close()
except Exception:
    pass
```

`tqsdk_stat` 的 10 处命中（1340/1367、2756/2783、3952/3979、4822/4849、5770/5797）**每个回测入口都是「先 close 再读 stat」成对出现**，无一处遗漏。

### 2.4 异常分流（L1301-1366）

```python
except Exception as _兜底异常:
```
分流为三类：BacktestFinished（正常结束）/ 拒单（「遇到错单」「开仓资金不足」「平仓资金不足」→ 提前结束 + 显著标注）/ 其它**原样 raise，绝不掩盖**。

**判定：✅ 无问题。**

## 三、手数与成本口径（#197）

### 3.1 边界一律「判正不判负」（NaN 防护）

engine 全文统一写成 `not (x and x > 0)`，而非 `not x or x <= 0`。
原因（代码内注释原文）：`float('nan')` 是 truthy、且 `nan <= 0` 恒为 False，写判负会让 NaN 漏过去，
后果**不是报错而是「永不触发」的静默失效**，最难查。

命中位置：
- `_dual_ma_stop_line` L156-159
- `channel_gate_ok` L641-647
- `_read_float_profit` L690-696
- `_risk_budget_hand` L350-362

### 3.2 保证金风控：两把尺

| 用途 | 取值 | 理由 |
|---|---|---|
| 算手数 | 固定 `init_balance` | 保证回测可加性（手数不随浮盈漂移） |
| 保证金上限 | 当前账户权益 `margin_equity=_meq` | 账户缩水时自动收紧 |

`_cap_hand < hand_min` 时**返回 0**（不发买不起的单，也不中断回测）。
L385-393 留有「★ 2026-09-28 修正（修复『高保证金品种死亡螺旋』bug）」记录。

### 3.3 成本口径诚实披露

`_cost_note_text`（L6172-6196）明确写出：
- ACTIVE 对价天然再吃 1 跳；
- PASSIVE 挂单「真实成交率回测无法反映，**须以模拟盘实测为准**」。

成本通过 `sim.set_commission` 走 TqSim 官方撮合，不由策略自算。

**判定：✅ 无问题。**

## 四、未来函数防护（#198）

### 4.1 通道轨道 `.shift(1)`

回测（L1033-1040）与模拟盘（L2055-2064）**两处逐字同源**：

```python
.up.rolling(n).max().shift(1).iloc[-2]
```

并各有显式注释说明「必须 shift 掉刚收盘那根，否则用当根自己的高点算轨道 = 未来函数」。

### 4.2 信号取值

所有决策函数的输入一律取 `.iloc[-2]`（**刚收盘的那根**），
MA 闸门 / 开盘保护 / 保证金计算 / ATR 全部用同一根的 close。**没有一处取 `.iloc[-1]`**。

### 4.3 仓位守卫用实际值而非意图值

`run_live` 的守卫看**实际持仓** `_pos_guard = int(api.get_position(cur_sym).pos)`
（L2075-2083），而不是内存里的 `want` —— 防止「想平但没平掉」时误判为空仓。

同一处注释明确写着：「**回测那份守卫故意不改**，改了会动 v1~v6 信号序列、整本账对照就废了」——
这是**刻意的口径隔离**，不是遗漏。

**判定：✅ 无问题。**

## 五、止损与出场顺序（#199）

### 5.1 止损合成全表（本轮逐条验证）

静态扫描出 engine 全部止损合成行，逐条判定「是否可能落到入场价有利侧」：

| 位置 | 合成式 | 是否安全 | 理由 |
|---|---|---|---|
| L163-172 `_dual_ma_stop_line` | `line = max(line, entry)` / `min(line, entry)` | ✅ | 终点是 `entry` 本身，不会越过到有利侧 |
| L3575-3589 `align` 支 | `stop = max(stop, soft)` | ✅ | **有显式守卫 `if soft > entry:`**（L3585） |
| L5380-5395 `pro` 多头 | `stop = max(stop, soft)` | ✅ | **已夹紧**（见 5.2） |
| L5419-5429 `pro` 空头 | `stop = min(stop, soft)` | ✅ | 镜像夹紧（见 5.2） |
| L4572-4772 `swing` 支 | `entry_px ∓ stop_atr×ATR`，同根锁定 | ✅ | **结构上不存在两刻度互越**，天然免疫 |

### 5.2 pro 支死路径修复留证（L5387-5394）

```python
soft = ext_high - P["trail_atr_mult"] * snap["atr"]     # 峰值回撤追踪
#★ 2026-10-08 修死路径：soft 必须夹在入场价不利侧。
#   soft = ext_high − trail×ATR，与 entry 无任何约束关系；ext_high 是
#   持仓期间最高价（含跳空高开），当 trail×ATR 小于 ext_high−entry 时
#   soft 会落在 entry **上方** ⇒ 多头止损价高于成本 ⇒ 下一根……
```

危险机理：`ext_high − trail×ATR` 可能落在入场价**上方** ⇒ 多头止损价高于成本 ⇒
下一根 `low <= stop` 立即成立、**凭空盈利**。
注释注明「与 06_MA13 的 swing 支同款 bug，**这里是唯一一处**」。

> ⚠️ **重要更正**：此注释中「这里是唯一一处」指的是「**pro 决策函数内**的唯一一处」。
> 本轮复查确认：`align` 支（L3585）**更早就已有同类守卫** `if soft > entry:`，
> 而 `swing` 支结构上不含此模式。即 —— **引擎内的同类防护共 2 处（align + pro），
> 不是「只有 1 处」**。这是对原注释范围的补充澄清，不构成新 bug。

### 5.3 出场时序（failsafe）

`_read_float_profit` **必须在 `set_target_volume(0)` 之前调用**（仓位一清 float_profit 就归零）。
回测（L1118-1125）与模拟盘（L2114-2124）两处均注明。

**判定：✅ 无问题（含 1 处已修留证 + 1 处注释范围补充）。**

### 6.2 `_drawdown_svg` / `_equity_svg` 的口径（C 级说明）

## 七、运行时健壮性（本轮补充维度）

### 7.1 `wait_update` 铁律：21 处全部合规

```
grep -c 'wait_update('                 →  21
grep -c 'wait_update(\s*)'             →   0     ← 无参调用 0 处
```

`while True` 主循环 11 处（973/1963/2572/3047/3674/4167/4651/5009/5590/5933），
**全部以 `wait_update(deadline=time.time()+30)` 起始**。休市永久阻塞的风险已全数消除。

### 7.2 五个模拟盘入口的恢复策略对比

**这是本轮最容易被误判「漏防护」的地方，特此说明：**

| | `run_live` | `run_live_boll` | `run_live_align` / `_swing` / `_pro` |
|---|---|---|---|
| 状态权威 | 内存 `want` + 对账五态 | 云端 `get_position` 直读 | 云端直读（同 boll） |
| 幽灵止损防护 | `_pos_guard` 显式守卫 | 天然免疫 | 天然免疫 |
| 断线处理 | 原位继续（靠 reconcile 纠偏） | **整体重跑会话体** | 同 boll |
| 持久化 | `_ledger` 账户流水 | `_boll_state.json` 精确恢复 | 同 boll |
| `wait_update` 带参率 | 8/8 | 2/2 | 5/5 · 5/5 · 3/3 |

`run_live_boll` 之所以**不需要** `_pos_guard`，是因为它不监听成交回报、而是
**直接用 `api.get_position(cur_sym)` 读云端真实持仓**（L3714-3716），
并用 `while api.get_position(cur_sym).pos != 0` 阻塞等成交（L3682）。

engine 自己的 docstring 已写明这个设计差异（L3377-3378）：
> engine 是「内存 want → 问云端」，刚下单时 want 已等于目标手数，
> `want == pos_now` 天然成立，不会把刚开的仓误判成外部遗留持仓。

**判定：✅ 两条路线均为自洽设计，不是遗漏。**
（横向对比确认：`run_live` 需要 `_pos_guard` 是因为它常驻单会话、必须热处理不一致；
`run_live_boll` 用冷启动重建，从源头不需要这个守卫。）

### 7.3 换月处理（L976-998）

`api.is_changing(quote, "underlying_symbol")` → 平旧仓（带 `_guard < 2000` 上限）→
换 `cur_sym` → 重建 `TargetPosTask` → 重设 commission → 恢复 `want`。链路完整。

### 7.4 成交监听字段修复留证（L1966-1989）

注释记载：`.symbol` → `.instrument_id` 修复。
> 原先直接写 `t.symbol` 会抛 AttributeError，把整个模拟盘进程带崩。

**判定：✅ 无问题。**
